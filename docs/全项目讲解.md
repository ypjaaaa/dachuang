## 一、一句话说清这个项目

> **把会议录音自动变成"能搜索、能问答、能定位到秒"的知识库,而且全程跑在你自己的电脑上,数据不上云。**

拆开看三个关键词:
- **多模态会议内容转化**:音频/视频 → 文字(转写),是"转化";
- **向量知识库**:文字 → 向量(数字),存进数据库,是"知识库";
- **RAG(检索增强生成)**:提问时先检索、再让大模型基于检索结果回答,是"智能问答"。

## 二、四个核心概念(答辩必讲)

### 2.1 什么是 RAG(检索增强生成)

**大白话**:让大模型"先查资料,再回答问题",而不是凭记忆瞎编。

**技术流程**:
```
用户提问
  → 检索:从知识库找出与问题最相关的几段内容
  → 增强:把这几段内容 + 问题一起喂给大模型
  → 生成:大模型基于"喂进来的资料"组织答案
```

**三个价值**(PPT 第 4 页写的,答辩要能展开):
1. **防幻觉**:答案基于检索到的真实资料,不编造;
2. **易更新**:新增会议只需入库,不用重新训练模型;
3. **可追溯**:每个答案都能指向原始会议片段和时间戳。

### 2.2 什么是向量与向量检索

- **向量**:把一段文字用模型变成一个数字列表(本项目是 1024 个数字)。语义相近的文字,数字列表也"接近";
- **向量检索**:给定问题的向量,在数据库里找"最接近"的向量 = 语义检索。所以问"性能怎么变慢了?"能搜到会议上说"CPU 飙到 90%"的内容,即使没有相同关键词。

### 2.3 什么是 Embedding(嵌入)模型

把文字变成向量的模型。本项目用 **bge-large-zh-v1.5**(中文检索榜单领先),输入文字、输出 1024 维向量。

### 2.4 什么是混合检索 + 重排序(Rerank)

单靠向量检索有短板(专有名词、人名不敏感),所以用**两路检索**再融合:
1. **向量检索**:找语义相近(懂"意思");
2. **BM25 关键词检索**:找字面匹配(懂"专有名词",如 "HBase"、"rowkey");
3. **RRF 融合**:两路结果按排名加权合并;
4. **Rerank 精排**:用交叉编码器(bge-reranker)对候选逐对打分,把真正相关的顶上来。

效果实测:检索准确率从纯向量 ~70% 提升到 **83.3%**。

## 三、系统端到端数据流(全项目主线)

```
┌──────────────────────────────────────────────────────────────┐
│ ① 输入:会议音/视频文件(MP3/WAV/M4A)                            │
│                                                              │
│ ② asr.py    语音识别(faster-whisper large-v3)                 │
│             输出:[{start: 0.6, end: 5.1, text: "大家好..."}]  │
│                                                              │
│ ③ chunk.py  智能分块(按语义边界切,保留时间戳)                   │
│             输出:[{text: "...", start: 46.28, end: 77.98}]    │
│                                                              │
│ ④ embed.py  向量嵌入(bge-large-zh-v1.5)                       │
│             输出:每块文本 → 1024 维向量                         │
│                                                              │
│ ⑤ ingest.py 入库(Milvus Lite)                                 │
│             存:向量 + 原文 + 起止秒 + 来源 + 标题 + 日期        │
│                                                              │
│ ⑥ retriever.py 混合检索(向量 + BM25 → RRF → Rerank)           │
│             输入:用户问题;输出:最相关的 top-k 段(带时间戳)      │
│                                                              │
│ ⑦ query.py   组装 Prompt → llm.py 本地大模型生成               │
│             输出:答案 + 引用列表[{标题, 起止秒, 相关度}]        │
│                                                              │
│ ⑧ ui.py     Gradio 界面展示(上传/问答/引用)                    │
└──────────────────────────────────────────────────────────────┘
```

**核心设计思想**:每一步都保留"时间戳",让最终答案能"指回"原始音频的秒级位置——这是和普通聊天工具最大的区别,也是答辩的差异化卖点。

## 四、代码逐模块讲解(app/ 目录)

> 全项目 10 个 Python 文件,共 712 行。按数据流顺序讲。

### 4.1 config.py —— 全局配置(45 行)

项目的中枢,所有路径和参数都在这:
- 路径:`MODELS_DIR`(模型)、`DATA_DIR`(数据)、`MILVUS_DIR`(向量库);
- 模型:`ASR_MODEL` / `EMBED_MODEL` / `RERANK_MODEL` / `LLM_GGUF`(指向 ModelScope 下载的本地目录,不联网);
- **设备自动检测**(重要):
  ```python
  try:
      import torch
      DEVICE = "cuda" if torch.cuda.is_available() else "cpu"
      LLM_GPU_LAYERS = -1 if DEVICE == "cuda" else 0
  ```
  启动时检测 GPU,可用就全速 GPU,不可用自动 CPU 兜底——**无需手动改配置**。

### 4.2 asr.py —— 语音识别(46 行)

- 用 `faster-whisper`(OpenAI Whisper 的加速版)加载 large-v3 模型,int8 量化省显存;
- `vad_filter=True`:自动过滤静音段;
- 输出带**起止时间**的句子列表:
  ```python
  [{"start": 0.6, "end": 5.1, "text": "欢迎大家来体验达摩院推出的语音识别模型。"}]
  ```

### 4.3 chunk.py —— 智能分块(58 行)

- 把转写出的句子**按语义边界合并**成知识块(句号/问号/长度触发切分),默认目标 500 字符、80 字符重叠;
- 超长块用 LangChain 的递归切分器二次切,避免"一刀切"割断语义;
- **每个块都带 start/end 时间戳**,这是可溯源的基础。

### 4.4 embed.py —— 向量嵌入(27 行)

- `SentenceTransformer` 加载 bge-large-zh-v1.5;
- `normalize_embeddings=True`:归一化,余弦相似度直接可比。

### 4.5 ingest.py —— 入库管道(122 行)

- 串起 ①②③④:转写 → 分块 → 嵌入 → 写入 Milvus Lite;
- 建库:`dimension=1024, metric_type="COSINE", id_type="string"`(字符串 UUID 主键);
- 每条记录:`{id, vector, text, start, end, source, title, date}`;
- 命令行用法:
  ```bash
  ./venv/bin/python -m app.ingest data/audio/会议.m4a "组会-0822" "2026-08-22"
  ```

### 4.6 retriever.py —— 混合检索(120 行,核心亮点)

本项目最有技术含量的模块,四步:
1. `_vec_search`:问题向量化 → Milvus 余弦检索 top-20;
2. `_bm25_search`:jieba 中文分词 → BM25 关键词检索 top-20;
3. `_rrf_fuse`:RRF 融合(`1/(k+rank)`,k=60)合并两路;
4. `_rerank`:bge-reranker-v2-m3 对 top-30 候选交叉编码打分,取 top-k;
5. 阈值过滤:相关度 < 0.01 的噪声段落剔除。

### 4.7 query.py —— 问答编排(67 行)

- `retrieve()`:调混合检索,过滤低分;
- `build_prompt()`:把检索结果组装成"摘录(带时间戳)+ 问题";
- `answer(query, history)`:完整问答;
- **多轮对话**:`rewrite_query()` 用大模型把追问重写为独立检索词:
  > "那修复方案呢?" → "HBase查询变慢的修复方案是什么?"
- 输出 `{answer, citations, search_query}`。

### 4.8 llm.py —— 本地大模型(79 行)

- `llama-cpp-python` 加载 Qwen2.5-7B GGUF(Q4_K_M 量化,4.4GB),分片自动合并;
- 走 **chat 模板**接口(create_chat_completion),输出干净不重复;
- `rewrite_query()`:复用同一模型做检索词重写;
- `n_gpu_layers` 由 config 自动决定(有 GPU 全上,无则 CPU)。

### 4.9 ui.py —— Gradio 界面(51 行)

- 两个页签:「① 导入会议」(上传音频+标题+日期,一键入库)、「② 智能问答」(聊天式提问);
- 把聊天记录转成标准 history 传给 answer(),支持多轮追问;
- 答案下方显示引用:时间段 + 标题 + 相关度。

### 4.10 evaluate.py —— 检索评测(42 行)

- 内置 6 道标注测试题(问题 → 期望命中的段落);
- 跑一遍算出"检索准确率":
  ```
  检索准确率: 5/6 = 83.3% (目标 ≥80%)
  ```
- 这是 PPT 验收指标"问答检索准确率 ≥80%"的量化工具。

### 4.11 download_models.py —— 模型下载(55 行)

- 从 **ModelScope**(国内可达)下载全部模型,SDK 目录也重定向到项目内;
- 支持按需下载:asr / embed / llm / all。

## 六、关键技术选型与"为什么"(答辩高频)

| 环节 | 选型 | 为什么 |
|---|---|---|
| ASR | faster-whisper large-v3 | 中文准确率高、本地可跑、int8 量化省资源 |
| 分块 | 时间戳语义分块 | 保留时间戳;避免固定长度切碎语义 |
| 嵌入 | bge-large-zh-v1.5 | 中文检索榜单领先,CPU 可推理 |
| 重排 | bge-reranker-v2-m3 | 对检索结果精排,准确率提升最明显的一步 |
| 向量库 | Milvus Lite | 嵌入式零运维、pymilvus 官方支持、数据单文件 |
| 生成 | Qwen2.5-7B GGUF Q4 | 中文强、4.4GB 量化版普通电脑可跑、本地不联网 |
| 界面 | Gradio | 上传/聊天组件现成,快速交付 |
| 模型来源 | ModelScope | 国内可访问(实测 HF 不可达) |

**项目定位**(答辩核心话术):**不发明新算法,而是把成熟开源组件做成本地化的整合方案**——这正是项目的价值和可行性所在。

## 九、局限与扩展方向(答辩"展望"部分)

| 现状 | 局限 | 扩展方向 |
|---|---|---|
| 无说话人分离 | 分不清谁说的 | WhisperX + pyannote,按说话人过滤检索 |
| 仅音频 | PPT/白板内容无法理解 | 图像识别(OCR/多模态)入库 |
| 单机 | 无法多人协作 | Web 服务化 + 账号体系 |
| 转写有错字 | 专有名词易错 | 热词表、专业领域微调 |
| LLM 走 CPU | 生成偏慢 | 装 CUDA Toolkit 重编译,GPU 生成 ~10 秒 |

## 十、答辩要点清单(3 分钟版)

1. **问题**:组会/课程录屏几十 G,知识被"冷冻",无法检索;现有工具要么功能弱要么要上传云端;
2. **方案**:RAG + 向量知识库,全本地部署;
3. **演示**:上传音频 → 转写 → 问"HBase 为什么慢?" → 答出原因+修复方案,带时间戳引用;
4. **亮点**:检索准确率 83.3%、防幻觉(无依据明确说"未找到")、多轮追问、Docker 一键部署、数据零上云;
5. **定位**:成熟开源组件的本地化整合,门槛低、易落地。
