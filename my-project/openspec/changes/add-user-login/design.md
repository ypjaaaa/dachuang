## Context

全新项目，尚无既有代码或数据模型（见 proposal.md - Why）。本次交付为纯后端 API，采用 Python + FastAPI。需要一个可验证登录的持久化用户来源，但注册功能不在本次范围（见 spec.md 的 `user-auth` 需求）。

## Goals / Non-Goals

**Goals:**

- 提供 `POST /auth/login` 端点，凭据校验通过返回 JWT 访问令牌。
- 密码仅以 bcrypt 哈希存储与校验。
- 无效凭据返回统一的 401 错误，避免账户枚举。
- 采用可替换的用户存储抽象，便于后续升级数据库。

**Non-Goals:**

- 用户注册、修改密码、登出/令牌吊销。
- 令牌刷新、多因素认证、OAuth/第三方登录。
- 前端登录页面。
- 生产级部署（TLS、限流、审计日志等）。

## Decisions

### 1. 密码哈希：bcrypt

- **选择**：使用 `passlib[bcrypt]`（底层 bcrypt）对密码做哈希。
- **理由**：成熟、有慢哈希（work factor）天然抗暴力破解，生态支持好。
- **备选**：argon2（更强但依赖更重）、pbkdf2（需手动调参）。本次选 bcrypt 兼顾简单与安全。
- **约定**：`bcrypt` 的 work factor 设为 12，哈希格式为 `$2b$...`，通过 `passlib` 的 `CryptContext` 统一封装，校验用 `verify`（哈希内已含 salt）。

### 2. 访问令牌：JWT

- **选择**：签发 JWT（`PyJWT`），HS256 签名，payload 含 `sub`（用户名）与 `exp`（过期时间）。
- **理由**：无状态，无需服务端会话存储，适合纯后端 API。
- **备选**：不透明会话令牌（需服务端存储与查询，增加状态）、SAML/OAuth（超出范围）。
- **约定**：过期时间默认 24 小时（可配置）；签名密钥从环境变量 `AUTH_SECRET_KEY` 读取，绝不硬编码。

### 3. 用户存储：SQLAlchemy + SQLite（仓库抽象）

- **选择**：SQLAlchemy ORM + SQLite 文件库，定义 `users` 表（`username` 唯一、`password_hash`）。
- **理由**：零外部依赖、快速启动；通过 `UserRepository` 接口隔离，后续可平滑切换到 PostgreSQL 等。
- **备选**：内存字典（重启即丢，无法作为真实凭据来源）、直接上 PostgreSQL（增加部署复杂度，与当前范围不符）。
- **约定**：仓库接口暴露 `get_by_username(username) -> User | None`；登录服务只依赖该接口。

### 4. 错误语义与账户枚举防护

- **选择**：用户名不存在与密码错误统一返回 `401` 与相同错误文案；字段缺失/类型错误由 Pydantic 校验返回 `422`。
- **理由**：满足 spec 对「不泄露账户是否存在」的约束，`422` 复用 FastAPI 默认行为。
- **约定**：响应体使用统一的错误结构（`{"detail": "..."}`），不区分具体失败原因。

## Risks / Trade-offs

- **[密钥泄露]** JWT 签名密钥若泄露，攻击者可伪造令牌 → 密钥仅存于环境变量，代码中不出现；文档标注生产需更换强随机密钥。
- **[账户枚举（时间侧信道）]** 对不存在用户跳过 bcrypt 校验会导致响应更快，可能被探测 → 对不存在的用户也执行一次 dummy bcrypt 校验以拉平耗时（实现于任务中）。
- **[SQLite 并发/生产局限]** SQLite 不适合高并发写 → 通过 `UserRepository` 抽象，后续可切换到 PostgreSQL 而无需改登录逻辑。
- **[JWT 无状态吊销]** 登出后令牌在过期前仍有效 → 本次范围不含吊销，记录为已知限制。

## Migration Plan

- 本项目为全新仓库，无数据迁移或回滚需求。
- 启动时由 ORM 建表（或提供 `alembic` 初版迁移）；用户数据通过后续流程或脚本写入（注册不在本次范围）。
- 回滚：删除新增的路由注册与依赖即可回到无登录状态，无破坏性影响。
